# Architecture Overview

This repository has now converged from a template into a local `computer-use` project. The main line is still a Swift-implemented macOS automation MCP server — 9 Computer Use tools, plus the opt-in, macOS-only `decide_next_action` advisory tool — and experimental Windows and Linux runtimes have been added, exposing the same baseline set of 9 Computer Use tools via standalone Go binaries.

## Current Directory Structure

- `apps/OpenComputerUse`
  The main entry point, responsible for CLI commands such as `mcp`, `doctor`, `list-apps`, `snapshot`, `call`, `turn-ended`, and global flags like `-h` / `--help` / `-v` / `--version`; when launched without arguments it first checks permissions, and only enters the dockless app-mode permission onboarding window when permissions are missing — `doctor` likewise only brings up this onboarding UI when it detects missing permissions.
- `apps/OpenComputerUseFixture`
  A local GUI fixture app used to host low-risk, predictable click/type/scroll/drag verification paths.
- `apps/OpenComputerUseSmokeSuite`
  An end-to-end smoke runner that brings up the fixture and MCP server and makes real calls to the 9 tools via JSON-RPC; it also supports a standalone visual cursor idle smoke test that uses a cross-process observation file to assert that, while waiting for the next move, the cursor shows an anchored tip with a tiny rotate wobble rather than lateral drift.
- `apps/OpenComputerUseWindows`
  An experimental Windows runtime. It does not depend on Swift or a `.app` bundle; the Go CLI/MCP entry point embeds a PowerShell UI Automation bridge, the build artifact is `open-computer-use.exe`, and it is distributed as a bundled artifact under the existing npm package's `dist/windows/<arch>/`.
- `apps/OpenComputerUseLinux`
  An experimental Linux runtime. It does not depend on Swift or a `.app` bundle; the Go CLI/MCP entry point embeds a Python AT-SPI bridge, the build artifact is `open-computer-use`, and it is distributed as a bundled artifact under the existing npm package's `dist/linux/<arch>/`.
- `packages/OpenComputerUseKit`
  The core library, containing:
  - MCP stdio transport and tool registry
  - app discovery
  - Accessibility / window snapshot
  - keyboard/mouse input simulation
  - software cursor overlay
  - fixture test bridge
- `experiments/CursorMotion`
  A standalone Swift cursor motion lab used to experiment with the `Bezier + arc + spring` parametric model, a parameter-tuning UI, and independent rendering; it is not directly coupled to the main MCP runtime.
- `experiments/StandaloneCursor`
  A new standalone Swift cursor viewer that directly reuses the candidate paths, scoring, and raw spring timeline converged upon in `scripts/cursor-motion-re/official_cursor_motion.py`, used to observe behavior that more closely matches the binary lift.
- `scripts/`
  Repository-level automation commands, including smoke tests, the `.app` packaging entry point, the Windows `.exe` / Linux binary build entry points, npm distribution scripts, and `scripts/computer-use-cli/`, a Go helper for probing the official bundled `computer-use`.
- `skills/`
  An installable skill for agent runtimes. Currently `skills/open-computer-use/SKILL.md` serves only as a lightweight entry point and index; details on installation, MCP/CLI usage, and troubleshooting are split out into adjacent `references/` files that load on demand; `scripts/package-skill.sh` handles validating and packaging the `.zip` / `.skill` artifacts.
- `docs/`
  Reverse-engineering analysis, execution plans, history, and project conventions.

## Runtime Layers

### 1. App Mode Layer

- By default, `OpenComputerUse`'s app mode brings up `PermissionOnboardingApp`.
- The app bundle runs in `LSUIElement` agent style, not exposing a persistent Dock icon by default, but it can still show the permission window on demand.
- When a user runs the macOS version of `open-computer-use mcp`, `doctor`, `call`, `snapshot`, or `list-apps` from a terminal, the CLI first launches the hidden app agent of the same `.app` bundle via LaunchServices, and forwards the request through a Unix domain socket under the user's temp directory; the process that actually calls Accessibility, ScreenCaptureKit, and the action tools is always `Open Computer Use.app`, never the iTerm / Terminal / Node launcher. The default socket filename is kept for historical compatibility; an embedding host can set `OPEN_COMPUTER_USE_AGENT_SOCKET_NAMESPACE` to use a private socket keyed to a namespace digest, avoiding sharing an agent with other OCU bundles.
- The CLI and MCP proxy forward `OPEN_COMPUTER_USE_*`-prefixed environment variables from the calling process to the app agent along with the request, and only temporarily override the agent's environment for the duration of that request; this ensures that `click_method=global`'s process-level safety gate and debug toggles still take effect per the caller's configuration under the app-agent architecture.
- The main window is responsible for rendering the `Accessibility` / `Screen & System Audio Recording` permission cards, the `Allow` / `Done` state, and state convergence after a relaunch; when both permissions are complete it closes automatically and no longer requires the user to quit manually.
- The auxiliary drag panel navigates to the corresponding `System Settings` page; after clicking `Allow`, the panel enters with a spring + curved-frame animation starting from the button's position in the main window, then settles at the bottom edge of the `System Settings` content area. By default the panel stays horizontally centered below the window's right-hand content area and pinned near the window's bottom edge, no longer relying on live-scanning the `+ / -` control row inside the permissions page; its window level is explicitly placed above the current `System Settings` window to avoid being covered by the permissions list content, while minimizing interference with System Settings' own scroll area. The panel also has an explicit back button, letting the user interrupt the current guidance and return to the onboarding main window to reselect a permission step.
- Permission state merges TCC's persisted authorization records with the current app process's runtime preflight: if any matching client is authorized in TCC, it is treated as granted, avoiding inconsistent authorization results seen by the CLI subprocess versus the GUI app; if the current `.app` process has already passed `AXIsProcessTrusted()` / `CGPreflightScreenCaptureAccess()`, it is likewise immediately treated as granted, avoiding a stale or mismatched TCC path record keeping the onboarding overlay lingering. The official release is still based on the `Open Computer Use.app` built by CI, while local debug/dev builds are now explicitly named `Open Computer Use (Dev).app`, and at dev-bundle runtime the current dev copy is preferred, avoiding two entries with exactly the same name appearing in System Settings.

### 2. MCP Layer

- The external transport facing the MCP host is still `stdio`; there is an extra local Unix domain socket proxy layer between the macOS terminal CLI and the `.app` app agent, used to ensure real automation runs under the app bundle's permission identity.
- This socket has **peer authentication** (`SocketPeerAuthenticator` + the pure-policy `AppAgentPeerAuthPolicy`): `acceptLoop` first validates same-uid via `getpeereid` for each connection, then requires the peer to satisfy `anchor apple generic and identifier "<agent bundle id>" and certificate leaf[subject.OU] = "<agent TeamID>"` via a `LOCAL_PEERTOKEN` audit token + `SecCodeCopyGuestWithAttributes` (same developer signature, pinned to this app's bundle identifier; when the agent is not running as a bundle, only the team is pinned). Unsigned dev builds fall back to same-uid only (printing a one-time notice). See `docs/SECURITY.md` for details.
- When `OPEN_COMPUTER_USE_VISUAL_CURSOR` is not explicitly disabled, the `mcp` command switches to a minimal AppKit runtime: the main thread keeps an event loop to host the overlay UI, while the stdio server still serially reads and responds on a background thread.
- Request framing uses one JSON-RPC message per line.
- Currently supported methods:
  - `initialize`
  - `notifications/initialized`
  - `notifications/turn-ended`
  - `ping`
  - `tools/list`
  - `tools/call`
- `notifications/turn-ended` is the open-source version's explicit turn-boundary hook; upon receipt it cleans up the visual cursor overlay in the current process. The CLI `open-computer-use turn-ended [payload]` also notifies the running AppKit MCP process to perform the same kind of cleanup via a macOS distributed notification, used to hook into the after-agent payload of Codex's legacy notify.

### 3. Tool Service Layer

- `ComputerUseService` is responsible for mapping Computer Use tool requests to local capabilities, while `ComputerUseToolDispatcher` consolidates the argument parsing and service-method dispatch for 9 Computer Use tools, plus the opt-in, macOS-only `decide_next_action` advisory tool, into a single layer shared by the MCP server and `open-computer-use call`.
- `list_apps` fetches app bundles in the standard application directories via a Spotlight metadata query and reads system metadata such as `kMDItemUseCount` / `kMDItemLastUsedDate_Ranking`; it then merges this with `NSWorkspace`'s currently running apps to output a view of "currently running + used in the last 14 days".
- `get_app_state` prefers real AX / window screenshots; a real app must have both a non-minimized `AXWindow` and a matching on-screen `CGWindow`. If the target app is merely hidden or temporarily has no on-screen window, it first does a best-effort unhide / activate / `open -b` / `AXRaise` with a brief retry, mirroring the official `computer-use` behavior of bringing Lark / Electron windows back before capturing; if it still cannot match after recovery, it returns the official-style `Apple event error -10005: cgWindowNotFound` rather than disguising the application root node or a screenshot-less window as an actionable state. When the target is the fixture app inside the repository, it falls back to the synthetic state exported by the fixture. By default, the real AX tree renders at most 1200 nodes and 64 levels deep on macOS, Linux, and Windows; an explicit `get_app_state` / `snapshot` call can override the budget via `max_tree_nodes` / `max_tree_depth`, but action tools' refreshed results still use the default budget. Snapshot text is truncated to 500 characters by default; an explicit `get_app_state` / `snapshot` call can override this via a positive integer `text_limit` or `"max"`, but action tools' refreshed results still use the 500-character default. For deep UIs such as Electron/WebView, empty `AXGroup` / `AXUnknown` wrappers are compressed, and `AXScrollToVisible` noise and empty string attributes are filtered, to avoid action-critical input fields being squeezed out of the node budget by semantically-empty containers; however, `AXPress` / `AXConfirm` / `AXOpen` child nodes within generic nodes form a text-summary boundary, so multiple clickable options are not merged into a single container. If such action nodes have a valid frame, a compact size, and no `AXLink` descendant carrying a URL, they are retained as a `button` with a window-relative `Frame`, using a short-text descendant as the button summary, so both icon-only and text-based web controls get a distinguishable `element_index`; when an `AXLink` descendant with a URL is present, the generic wrapper and the link child node are retained instead, so navigation links are not swallowed by the summary. For controls such as native open panels / Finder column view that place content in `AXContents` / `AXVisibleChildren`, visible file items are also included in the element tree. `get_app_state` also supports an optional `compact` boolean parameter: when set to true, it returns only actionable elements, flattens indentation, places the focused element first, and omits the window screenshot, to reduce the token cost of each call. "Actionable" does not equal "exposes an accessibility action": `set_value` only requires `AXValue` to be settable, and macOS text fields often declare no action at all, so `AXTextField` / `AXTextArea` / `AXComboBox` are always retained (querying settability element-by-element would require an extra AX round trip per node, an unacceptable cost); in fixture mode, `click` / `set_value` dispatch by identifier, so elements with an identifier are always retained. When the `compact` value cannot be parsed as a boolean, it errors out directly rather than silently falling back to the full tree — the latter would give a call that asked for the "cheapest" result the most expensive one instead. `compact` **does not renumber** `element_index`; the index stays consistent with the full tree, so `click` / `set_value` / `scroll` / `perform_secondary_action` can still be used directly; when context or a screenshot is needed, simply drop the parameter and call again. **`compact` is currently implemented only in the macOS Swift runtime**; the Linux and Windows Go runtimes each maintain their own tool schema and do not yet support this parameter — a known cross-platform capability gap.
- The MCP `tools/list` description / input schema currently converges on the official `computer-use`'s wording and parameter surface for the 9 Computer Use tools, plus the opt-in, macOS-only `decide_next_action` advisory tool when configured, minimizing drift in host-side prompts and tool surface.
- `open-computer-use call <tool> --args '{...}'` directly outputs an MCP-style JSON result; `open-computer-use call --calls '[...]'` / `--calls-file <path>` sequentially executes the tool calls in the JSON array within the same process, reusing the same `ComputerUseService` in-memory state, so action tools following a `get_app_state` can continue using the `element_index` from that same snapshot round. Sequential execution sleeps 1 second between successful adjacent operations by default, which can be overridden with `--sleep <seconds>`; it stops after encountering a tool result with `isError=true`.
- For `get_app_state` / action tool entry points against real apps, only a single password-manager bundle denylist layer is kept: a directly passed bundle-id returns a safety denial immediately; name matching does not resolve to these apps by default. Terminal, Chrome / Atlas, and system components are no longer built-in blocked targets.
- For ordinary apps, element frames are currently output as window-relative coordinates with the window's top-left corner as the origin, making it easier to unify `element_index` and screenshot coordinates onto a single reference frame going forward.
- Before and after performing a real action, `click` / `set_value` additionally drives a transparent `SoftwareCursorOverlay` window: both now share a heading-driven, official-style motion core for their move phase, explicitly feeding "the cursor's current heading" and "the final resting pose" together into the path chooser, preferring to generate a C-shaped/single-side large-arc trajectory that turns around first when needed and then proceeds along the nose direction; on first display it generates a starting point from the AppKit global `(0,0)` window origin, matching the official binary's fresh state, and subsequent actions continue to reuse the previous frame's visible tip. The cursor actually displayed is no longer directly equal to the path sample, but passes through an independent visual-dynamics state that continuously advances the visible tip, velocity, angle, and fog/offset. At the end of `click` a click pulse and a more noticeable but still small rotate wobble follow; `set_value` only does settle / idle, with no pulse; after either finishes, it continues holding an idle state at the target point, and while waiting for the next action the tip stays anchored with only a perceptible small-angle wobble; cleanup only happens after 30 consecutive seconds with no new action, so consecutive tool calls don't repeatedly start fresh from `(0,0)`; if the host issues `turn-ended` at the end of a task/turn, the cursor disappears immediately and this round's position state is cleared.
- The overlay's visual style no longer crops the small `SoftwareCursor` image from the official app bundle itself; the main MCP runtime now, like `CursorMotion`, preferentially renders the `official-software-cursor-window-252.png` baseline preserved in the repository, only falling back to `OpenComputerUseKit`'s internal procedural pointer/fog fallback when that asset is missing. The hit-point anchor remains fixed at the same tip-offset within the `126x126` canvas; the glyph's own neutral heading continues to follow `CursorMotion` / the official baseline's `-3π/4`. The main runtime's overlay window moves in AppKit global coordinates, so before feeding the y-down screen-space click target produced by AX / `CGWindowList` into the overlay, it is first converted to the corresponding screen's AppKit global coordinates; path selection uses the AppKit forward heading actually visible on screen, and before entering the visual-dynamics / render state, the velocity's y-axis is flipped back to CursorMotion's y-down screen state, which is then handed to the AppKit drawing layer for angle and `dy` flipping. The procedural fallback keeps the neutral artwork correction, aligning its natural silhouette axis to `CursorMotion` / the official baseline's `-3π/4` forward direction, but without making the experimental line depend on runtime code.
- The overlay's window level is no longer fixed at `.floating`; it now follows the target window id/layer hit by the snapshot, placing itself above that target window rather than crudely forcing itself above all foreground apps.
- The overlay's curved path is no longer generated purely from a fixed Bezier template; the current main line uses a heading-driven candidate family constrained by reverse engineering, keeping only the `direct` / `turn` / `brake` / `orbit` families that stably produce a single-side main arc, and continues to keep the target-window hit strategy as a tie-break among candidates of the same kind. The original `20` paths and scores recovered from the binary lift are still kept in the standalone `StandaloneCursor` viewer / Python reconstruction script for comparative analysis, and are no longer directly used as the runtime's default chooser.
- The overlay's progress curve is also no longer a fixed `easeInOut`; the main line now reuses the official spring/`VelocityVerlet` shape with `response=1.4`, `dampingFraction=0.9`, `dt=1/240`, and the default move duration is aligned to the recovered close-enough endpoint-lock time of `343 / 240 = 1.4291667s`, no longer additionally compressed by path distance.
- The overlay no longer relies on a temporary `terminal settle` patch to fix the tail; the main line has now uniformly moved to a two-layer model where "the path layer supplies the target point, the visual-dynamics layer supplies the visible pose", so the move's final segment, pulse, and idle all share the same state, and there is no longer a tail where, once the endpoint is locked, only an in-place angle flip remains.
- The overlay's render input has also expanded from a single `rotation` to `rotation + cursorBodyOffset + fogOffset + fogScale`, letting velocity lag genuinely show up on screen rather than existing only in the main loop's internal state; `rotation` is now approximated by the same layering as the binary's `SoftwareCursorStyle.angle + CursorView._animatedAngleOffsetDegrees`, no longer compressing "the main heading that follows the direction of motion" and "the small wiggle offset" into a single constrained small angle.
- Action-type tools use a "non-invasive first, physical-pointer path explicit opt-in" strategy for ordinary apps:
  - `perform_secondary_action` only executes AX actions already exposed by the target element; AppKit custom action descriptors like Safari's (e.g. `Name:close tab ...`) are shown with a short name that maps accurately back to the filtered original AX action, avoiding raw/rendered action mismatches; when a short name conflicts with another display name or any other original AX action (including filtered-out actions, case-insensitively), the full descriptor is kept, ensuring the output selector is not preempted by an exact match against a raw action; an invalid or ambiguous action returns the official-style `... is not a valid secondary action for ...`, and the fixture's `Raise` path no longer prepares global physical pointer input just for testing
  - `set_value` first uses `AXUIElementIsAttributeSettable(kAXValueAttribute)` to determine whether the target is genuinely a settable-value element, only calling `AXUIElementSetAttributeValue` when it is settable; when not settable, it returns the official-style non-settable error rather than falling back to keyboard input, the clipboard, or an undisclosed text-replacement interface
  - `click.click_method` is an optional extension in the open-source version, supporting `auto` (default), `accessibility`, `app_post`, `sky_click`, and `global`. When no parameter is passed, the original automatic routing continues to be used; explicit modes never silently fall back to another implementation. `accessibility` only accepts `element_index`; the other mouse paths can use `element_index`'s computed landing point or raw `x/y` coordinates.
  - The `auto` left-click path for an element-targeted `click` first tries native-list `AXSelectedChildren` selection, then tries genuinely semantic activation actions such as `AXPress` / `AXConfirm` / `AXOpen`; if the target itself is not clickable, it further tries its descendant AX elements (e.g. a cell exposing `AXOpen` under a Finder sidebar row) and AX hit-test results near the hit point, and finally falls into the existing non-AX branch: when the global-pointer environment variable is not enabled it uses `postToPid`-directed mouse events, and when enabled it directly uses global HID events. Activation-only fallbacks such as `AXRaise` / `kAXMainAttribute` / `kAXFocusedAttribute` are only allowed for window-level elements, to avoid an ordinary static text or container element misreporting "gained focus" as "click handled"; `click_count > 1` also prefers repeating an available AX action.
  - Explicit `click_method=accessibility` only executes the AX semantic actions above; explicit `click_method=app_post` bypasses AX candidates and descendant scanning, sending `mouseMoved` / down / up directly to the target process via `CGEvent.postToPid`; explicit `click_method=sky_click` accepts only left single/double clicks and only on macOS — it verifies that the current snapshot's `CGWindowID` is still owned by the same PID and on-screen, briefly puts the target app into a synthetic-active state only via `SLPSPostEventRecordTo` (never sending a defocus record to a genuinely foreground app), then sends a target move, a `(-1,-1)` primer, and the real down/up following a Chromium-compatible recipe. Each mouse event is delivered through both a dynamically-resolved `SLEventPostToPid` and the public `postToPid`, carrying window-local location, PID/window, and click-group fields; after the renderer settles, only the target's synthetic-active state is undone. `sky_click`'s action-result snapshot refresh also prohibits activate / `AXRaise` recovery, failing outright when the target state is momentarily unreadable. It does not change `auto`, and does not fall back if any step fails. Explicit `click_method=global` likewise bypasses AX but sends system-level pointer events via `.cghidEventTap`. `global` also requires `OPEN_COMPUTER_USE_ALLOW_GLOBAL_POINTER_FALLBACKS=1` to be set, otherwise the request is rejected before moving the visual cursor or sending input.
  - For a `text` summary line synthesized by the renderer, `click` no longer clicks the parent container's center by default; such elements use a left-side safe anchor instead. For descendant candidates of ordinary rows/containers/text, right-side compact hover actions are also filtered out (e.g. the "done" checkmark in a Lark/Electron conversation list), avoiding a main-row click being misfired as a side action; for WebArea-synthesized text in apps like Electron/Lark, it first looks for a nearby row-level `AXPress` ancestor and executes it silently, avoiding clicking the row with a physical mouse. Browser WebAreas (e.g. Chrome/GitHub) do not go through this Electron-scoped row-level-ancestor click optimization, and still use the generic link/container click path. If the hit point only resolves back to a page-spanning Electron/WebArea-level AX element, it no longer continues scanning the entire large container's descendant candidates, avoiding a single row click being intercepted by a distant clickable element.
  - `AXUIElementCopyElementAtPosition` performs coordinate hit-testing, resolving coordinate clicks back into actionable AX elements wherever possible
  - `CGEvent.postToPid` sends keyboard events in a directed manner, avoiding stealing the foreground for `type_text` / `press_key`; `type_text` batches text into small groups of `keyboardSetUnicodeString` events by Unicode extended grapheme cluster, avoiding Chinese punctuation, emoji/surrogate pairs, and combining characters being split apart per UTF-16 code unit and getting reordered or malformed inside Electron rich-text inputs. If the currently focused element's `AXValue` is settable, `type_text` prefers appending to the editable content and writing back `AXValue`; this covers the case where Feishu / Electron rich-text inputs unreliably receive background keyboard events, and it filters known placeholder hints to avoid splicing the placeholder into the draft; if the currently focused element is not an editable text target, `type_text` errors out requiring the caller to first click the text input area or use `set_value`, no longer treating an ineffective background keyboard delivery as success; `press_key`'s xdotool parser covers common aliases from the official binary's key table such as `BackSpace`, `Page_Up`, `Prior` / `Next`, `F1...F12`, and `KP_*`
  - `scroll.pages` aligns with the official `1.0.755`'s `number` schema, supporting fractional page counts; when the page count is an integer and the target exposes `AXScroll*ByPage`, it prefers the AX action, otherwise it sends a scroll event directed at the target process via `CGEvent.postToPid`
  - `drag` is still a coordinate-only API, but by default it no longer uses global `.cghidEventTap` mouse events; it now defaults to sending mouse move / down / dragged / up events directed via `CGEvent.postToPid`, avoiding moving the user's real hardware cursor; the `x/y` of these coordinate tools is first interpreted as screenshot-pixel coordinates, then mapped back to window-point / Quartz global coordinates based on the ratio between the screenshot's pixel dimensions and the target window's bounds, avoiding a Retina window's 2x pixels being mistaken for 1x points and causing the click to land in the wrong place
  - In the default configuration, with the environment variable not enabled, `click` / `scroll` / `drag` do not go through the global `.cghidEventTap`, so they never move or hijack the user's real mouse; `OPEN_COMPUTER_USE_ALLOW_GLOBAL_POINTER_FALLBACKS=1` is the process-level safety gate for the global-pointer capability, and explicit `click_method=global` must still pass through this authorization. The default path no longer calls `NSRunningApplication.activate` for the sake of a fallback. `drag`'s result includes a `Drag delivered via ...` text item after the snapshot text and before the screenshot, stating whether this call used the `app_post` directed delivery or the global-pointer path; on the default path it also states that `postToPid` events do not go through the window server, and therefore cannot drive window-server drag sessions such as window moving, text drag-selection, or Finder drag-and-drop. `drag`'s tool description likewise documents this limitation and the corresponding environment variable. Once the global path is explicitly enabled, dragging delivers to the HID tap using the default event source, interpolating by distance and writing a displacement delta at each step; on macOS 26+, the down / dragged / up events also share a single gesture-event number, letting the window server recognize the real drag session needed for window moving, text drag-selection, and Finder drag-and-drop

**Input simulation is PID-targeted by default.** All keyboard and mouse events are dispatched to the target app's PID via `CGEvent.postToPid` or AX `performAction`, so the target app does not need to be frontmost and the user's hardware cursor is never moved. Global pointer fallbacks (`clickGlobally` / `scrollGlobally` / `dragGlobally`) exist in the codebase but are gated behind `OPEN_COMPUTER_USE_ALLOW_GLOBAL_POINTER_FALLBACKS=1` and are never active in production use. This design enables full background operation — MCP tools can drive any app without stealing focus or disrupting the user's active workflow.

### 4. Lock Screen Guard & App-Screen Session

Three new modules were added, coordinated uniformly by `ComputerUseToolDispatcher` at the tool-call entry point:

**`MacSessionGuard`** (`packages/OpenComputerUseKit/Sources/OpenComputerUseKit/MacSessionGuard.swift`)
- Calls `CGSessionCopyCurrentDictionary` at every tool-call entry point to check the `CGSSessionScreenIsLocked` key.
- If the dictionary is missing, empty, or fails to parse → `isUnknown = true`, treated as locked (fail-closed), returning an error and recording a "Lock state unknown" indicator.
- **Lock-screen policy `MacSessionLockPolicy`** (`.fromEnvironment()` reads `OPEN_COMPUTER_USE_ALLOW_LOCKED`):
  - `.blockWhileLocked` (default): rejects all action tools while locked, behavior unchanged from before.
  - `.allowWhileLocked` (explicitly enabled via `OPEN_COMPUTER_USE_ALLOW_LOCKED=1`): permits all tools while locked, doing best-effort control. This is feasible because all actions use process-targeted delivery (AX `performAction`/`setAttributeValue` or `CGEvent.postToPid`, which by default does not go through the global HID event tap), which can still reach the target process while the login window occupies the screen. A one-time degradation notice is printed to stderr the first time this is allowed. **Limitations while locked**: window screenshots return an empty image (a system security restriction — `get_app_state` returns only the AX tree, with no image), and coordinate-only paths that depend on a visible cursor are unreliable — `element_index`-targeted actions should be preferred.
- `tools/list` calls are not intercepted by the lock guard.
- Protocol: `MacSessionStateProvider` (injectable for unit testing); real implementation: `SystemMacSessionStateProvider`.

**`AppScreenSession`** (`packages/OpenComputerUseKit/Sources/OpenComputerUseKit/AppScreenSession.swift`)
- Maintains `SnapshotIdentity` (pid, target window ID, window bounds, screenshot pixel dimensions, captureGeneration).
- Compares against the saved identity before executing an action call; if bounds exceed an 8pt tolerance, the windowID changes, or the pid/screenshot dimensions change → returns `appScreenStaleStateError`, requiring a fresh `get_app_state`.
- Updates the identity after a successful `get_app_state`; not cleared on turn-ended (reusable across consecutive turns).

**`ControlActivityStore`** (`packages/OpenComputerUseKit/Sources/OpenComputerUseKit/ControlActivityStore.swift`)
- Aggregates the state of all connections (idle / active / locked / permissionMissing / recentError).
- `ControlActivityEvent` carries only toolName, app name/bundle id, and pid — never args/text/screenshots.
- Subscribed to by `ControlStatusMenuController` to drive the status-menu UI.

**`ControlStatusMenuController`** (`apps/OpenComputerUse/Sources/OpenComputerUse/ControlStatusMenuController.swift`)
- Presents a macOS menu-bar status item when running in App Mode (app-agent), showing the connection count and recent activity.
- Restart menu item: enabled in app-agent mode; disabled in direct AppKit MCP mode (the host must restart the process itself).
- The diagnostic-text Copy action includes only metadata, never AX tree content or action parameters.

### 5. Fixture Bridge

- `OpenComputerUseFixture` writes its own window and element state to a temporary JSON file.
- For the fixture's `get_app_state` and a small number of test-only actions, an explicit command channel is used via `FixtureBridge`.
- This bridge serves only the deterministic smoke path within the repository; it is not the capability boundary for real third-party apps.
- Because a fixture launched as a bare SwiftPM executable has no stable bundle identifier, `list_apps` injects an internal synthetic identifier only for `OpenComputerUseFixture`, ensuring the smoke suite can still cover `list_apps`, while ordinary third-party apps are still output with their real bundle id.

### 5. Cursor Lab

- `StandaloneCursor` is a new standalone SwiftUI/AppKit demo target that can be launched locally via `swift run StandaloneCursor`.
- This line prioritizes validating the core already converged upon by the Python reconstruction script: the `20` candidate paths, `measure + score`, `prefer in-bounds then lowest-score` path selection, and the raw spring timeline of `response=1.4` / `dampingFraction=0.9` / `dt=1/240`.
- It deliberately does not introduce a speculative wall-clock duration mapping, nor does it reuse `CursorMotion`'s pose dynamics, which lean more toward visual-feel experimentation.
- `CursorMotion` is a separate SwiftUI demo target that can be launched locally via `swift run CursorMotion`.
- This line prioritizes validating the motion model itself: the current main line is the heading-driven turn / brake / orbit / direct candidate family, spring progress, independent visual dynamics, and a debug UI; the arrow angle actually drawn during the moving phase continuously follows the visual dynamics' main heading, smoothly returning to the default resting pose as it nears a stop, and retaining a small in-place wobble angle during idle.
- The lab's cursor visuals continue to reference `scripts/render-synthesized-software-cursor.swift`: preferring the official `252x252` runtime baseline image saved in the repository, falling back to the script's procedural pointer/fog approximation when it's missing; the settle state has also changed to a small, center-fixed wobble angle rather than continuing to drift slightly along XY.
- It currently does not connect to real tool calls, nor does it write back to the main `SoftwareCursorOverlay`, with the goal of isolating experimental noise from the boundary of product behavior.

### 6. Windows Runtime

- The Windows runtime lives at `apps/OpenComputerUseWindows`, maintaining the CLI, `call --calls` sequences, MCP JSON-RPC, tool schema, and in-process snapshot cache in Go.
- The build entry point is `scripts/build-open-computer-use-windows.sh --arch arm64|amd64`, outputting by default to `dist/windows/<arch>/open-computer-use.exe`; the npm release package bundles both Windows artifacts into the existing root/alias packages, and the Node launcher automatically selects based on `process.platform/process.arch`.
- The Go runtime carries `runtime.ps1` via `go:embed`, writing it to disk temporarily and invoking Windows PowerShell when a tool call executes. The PowerShell bridge uses `System.Windows.Automation` for app/window/element discovery, tree rendering, UIA pattern actions, ValuePattern set value, and ScrollPattern scroll; when the target app does not expose the corresponding pattern, it falls back to `PostMessage` / `SendMessage`-style Win32 window messages.
- By default the Windows runtime only connects to already-running apps; it does not automatically `Start-Process` when `get_app_state` can't find the process, nor does it allow the `SetFocus` secondary action by default; these two foreground-stealing paths require `OPEN_COMPUTER_USE_WINDOWS_ALLOW_APP_LAUNCH=1` and `OPEN_COMPUTER_USE_WINDOWS_ALLOW_FOCUS_ACTIONS=1` respectively to be explicitly enabled. By default, `type_text` prefers sending `EM_SETSEL` / `EM_REPLACESEL` to the writable text control's child HWND, and no longer defaults to the UIA `ValuePattern.SetValue` fallback that could trigger foreground activation; the old behavior requires setting `OPEN_COMPUTER_USE_WINDOWS_ALLOW_UIA_TEXT_FALLBACK=1`. The UIA pattern and Win32 message fallback are themselves still best-effort: many controls can respond in the background, but Windows has no single background keyboard/mouse input model equivalent to macOS AX across all GUI toolkits.
- The protocol surface of these 9 tools stays consistent with the macOS main line: `list_apps`, `get_app_state`, `click`, `perform_secondary_action`, `scroll`, `drag`, `type_text`, `press_key`, `set_value`. Element-targeted actions prefer reusing the runtime id / automation metadata from the previous `get_app_state` round, while coordinate actions use screenshot/window-relative coordinates.
- On Windows, `click_method=accessibility` maps to a UI Automation pattern, and `app_post` maps to HWND `PostMessage`; the macOS-only `sky_click` and the unimplemented `global` both explicitly return unsupported before the snapshot lookup. `auto` still keeps its existing behavior of UIA-first with window-message fallback.
- Windows UI Automation needs to run within a logged-in user's desktop session. When running as a background process detached from the desktop over SSH, PowerShell can still start and return JSON, but the system may not expose top-level windows to it; in that case `list_apps` will be empty, and `get_app_state` may return `appNotFound(...)`.
- The Windows side is currently still a functional first version: no visual cursor overlay, no installer/onboarding, no code signing, and no standalone Windows smoke fixture. Follow-up TODOs are recorded in `docs/exec-plans/active/20260422-windows-computer-use-runtime.md`.

### 7. Linux Runtime

- The Linux runtime lives at `apps/OpenComputerUseLinux`, maintaining the CLI, `call --calls` sequences, MCP JSON-RPC, tool schema, and in-process snapshot cache in Go.
- The build entry point is `scripts/build-open-computer-use-linux.sh --arch arm64|amd64`, outputting by default to `dist/linux/<arch>/open-computer-use`; the npm release package bundles both Linux artifacts into the existing root/alias packages, and the Node launcher automatically selects based on `process.platform/process.arch`.
- The Go runtime carries `runtime.py` via `go:embed`, writing it to disk temporarily and invoking `python3` when a tool call executes. The Python bridge uses the AT-SPI2 interface exposed by GNOME/GObject Introspection for app/window discovery, accessibility tree rendering, semantic actions, editable text, value set, and best-effort key/mouse fallback; text capability is detected via `Accessible.get_interfaces()` checking for `Text` / `EditableText`, not relying on convenience properties that may not exist across different PyGObject versions.
- On Linux, what most closely resembles macOS AX is AT-SPI2/D-Bus accessibility, not a unified background keyboard/mouse input model. The first version prioritizes the AT-SPI action, EditableText, and Value interfaces exposed by elements; coordinate `click` / `drag` and `press_key` use an AT-SPI event-synthesis fallback, which can only be handled best-effort under Wayland.
- The Linux runtime needs to run within a logged-in desktop user session. When `XDG_RUNTIME_DIR`, `DBUS_SESSION_BUS_ADDRESS`, or the display environment are missing, the Go runtime tries to auto-discover the current user's session bus and display/Wayland values from `/run/user/<uid>` and common desktop processes before launching the Python AT-SPI bridge; a plain SSH tty that cannot find a logged-in desktop session can still start the binary, but cannot directly inspect or operate the GUI session.
- `get_app_state`'s accessibility tree can be very deep on GTK/GNOME apps; the Linux bridge uses the same default tree budget of 1200 nodes and 64 levels as macOS/Windows, and supports explicitly raising `max_tree_nodes` / `max_tree_depth`. Screenshots are captured best-effort via the GDK root window; GNOME Wayland may return an all-black image, and the bridge detects an all-black sample and omits the image block.
- The protocol surface of these 9 tools stays consistent with macOS/Windows: `list_apps`, `get_app_state`, `click`, `perform_secondary_action`, `scroll`, `drag`, `type_text`, `press_key`, `set_value`. Element-targeted actions prefer reusing the runtime path metadata from the previous `get_app_state` round, while coordinate actions use screenshot/window-relative coordinates.
- On Linux, `click_method=accessibility` maps to an AT-SPI action, and `global` maps to AT-SPI mouse synthesis and requires the global-pointer environment variable; AT-SPI has no equivalent process-directed mouse dispatch, so `app_post` and the macOS-only `sky_click` both explicitly return unsupported before the snapshot lookup. `auto` still keeps its existing behavior of AT-SPI-action-first with mouse-synthesis fallback.
- The Linux side is currently still a functional first version: no visual cursor overlay, no installer/desktop entry, and no standalone Linux fixture. Follow-up TODOs are recorded in `docs/exec-plans/active/20260422-linux-computer-use-runtime.md`.

### 8. Local decision model (experimental)

- `decide_next_action` is an opt-in, macOS-only advisory tool implemented alongside the other Computer Use tools in `packages/OpenComputerUseKit/Sources/OpenComputerUseKit/` (`DecisionAdvisor.swift`, `DecisionModelClient.swift`, `DecisionModelTransport.swift`, `DecisionPrompt.swift`, `DecisionCandidates.swift`, `DecisionSidecarVerifier.swift`). `Package.swift` declares `.macOS(.v14)` only, so the Go-based Windows and Linux runtimes never gain it.
- Data flow for one call: the MCP host → the local Unix-socket proxy (`apps/OpenComputerUse/Sources/OpenComputerUse/MacOSAppAgentProxy.swift`) → the `.app` app agent's `ComputerUseService.decideNextAction` → candidate pruning and paging over the current AX snapshot (`DecisionCandidateBuilder`) → one or more `/completion` requests to a loopback `llama-server` sidecar → an advisory JSON result (operation, `element_index`, margins, and the full operation/target distributions) returned to the host. The server only ever proposes; it never performs the action itself.
- `tools/list` and `initialize` gate the tool per call: `ToolDefinitions.listed(environment:)` appends `decide_next_action` only when `OPEN_COMPUTER_USE_DECISION_MODEL_URL` parses from that call's own environment, and the cascade guide is appended to `initialize`'s instructions only in that case — so a host sees the tool, and the extra guidance for using it, only when it configured the sidecar itself.
- Unlike the shared app agent's other proxied calls, `decide_next_action` reads no other key from the process environment beyond the URL passed explicitly with the request, so the agent runs it without taking the process-wide environment-override lock that guards other hosts' calls; holding that lock for the call's network wait would otherwise block every other host sharing the agent. The whole advisory call is instead bounded by its own `DecisionAdvisor.overallDeadline` (12 s), checked before every model call, with each individual `/completion` request further bounded by `DecisionModelClient.defaultRequestTimeout` (5 s) — a well-behaved call returns or fails in roughly 17 s.
- The sidecar (`llama-server`, started by `scripts/decision-model/start-sidecar.sh`) is always user-started on a deterministic per-user loopback port; it is never spawned by the app agent, the MCP server, or any other script.

## Key Boundaries

- The open-source version currently does not replicate the official closed-source implementation's caller signing, private IPC, full overlay choreography, or plugin self-install logic.
- Because the official `SkyComputerUseClient` carries host-side launch constraints, a plain stdio MCP client may be killed outright by the system on the local machine; if probing the official bundled `computer-use`, `scripts/computer-use-cli`'s app-server mode is currently only suitable for tool-listing and protocol-surface observation. The official `1.0.755`'s real tool calls also go through service-side sender authorization / active IPC client tracking, and an external raw helper — even going through a signed Codex binary — may still return `Sender process is not authenticated`; genuine use of the official tools should go through the normal Codex agent/tool call chain, while the open-source version continues to offer a directly connectable `open-computer-use` MCP server.
- The current permission onboarding already has a runnable app, deep links, drag assistance, and a version of the accessory panel's entrance animation and back affordance that is closer to the official one; the click chain has also been supplemented with an independent visual cursor, official asset fallback, and ordering logic relative to the target window, and while the overlay is visible it continuously reasserts being "above the target window", avoiding the cursor being re-covered by the target window after the user manually activates the target app; overall, though, it has not yet fully replicated the official embedded choreography / host integration / session-approval experience.
- Screenshots currently capture the target window via `ScreenCaptureKit` and are returned as a base64 PNG in an MCP `image` content block, no longer writing ordinary app screenshots to disk in the repository or temp directory; before encoding, the image is adaptively downscaled to a max size and target byte count, avoiding a large PNG from a complex page triggering host-side MCP result degradation, while coordinate tools continue to map coordinates based on the actually returned screenshot pixel size; a single ScreenCaptureKit capture has a timeout set, after which the image block is omitted rather than the entire `get_app_state` call hanging.
- Session state is now in-process memory state, storing each app's most recent snapshot and element-index mapping.
