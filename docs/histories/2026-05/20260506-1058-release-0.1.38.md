### Execution Context

### User Query
> After `npm install -g open-computer-use`, `open-computer-use doctor` still times out.

### Changes Overview
**Scope:** macOS permission app selection, release version sources, release notes

**Key Actions:**
- **[App Selection Hotfix]**: When the current process comes from a legitimate `Open Computer Use.app` bundle, `currentAppBundleURL()` now prefers the currently running bundle, avoiding LaunchServices / Spotlight returning a stale staging app left over in the repo.
- **[Regression Test]**: Added a pure-function test locking down the selection rule "a running release bundle can override a stale installed copy."
- **[Version Bump]**: Uniformly bumped the plugin manifest, Swift/Go runtime version, smoke/test init version, and CLI helper example to `0.1.38`.
- **[Release Notes]**: Documented the fix for the `doctor` timeout caused by launching a stale copy after an npm install.

### Design Intent (Why)
`0.1.37` already forwarded macOS automation to the app-agent, but app discovery still trusted `NSWorkspace.urlForApplication(withBundleIdentifier:)` first. On a dev machine, LaunchServices could return the old `dist/npm/.../Open Computer Use.app` left in the repo, causing the new npm CLI to launch the old app-agent and time out. The `.app` the current process is running from is what the user actually executed as the npm artifact, and it should take priority as the agent launch target.
