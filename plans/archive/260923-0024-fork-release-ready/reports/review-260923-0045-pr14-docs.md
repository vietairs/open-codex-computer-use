# PR #14 — documentation accuracy & honesty review

Branch `chore/fork-release-ready` @ `c343431` vs `main` @ `0502c8b`.
Lens: is every added/changed sentence TRUE, and would a reader be misled?
Read-only review. Markers: **[RAN]** = command executed here, **[READ]** = source inspection.

## Verdict

The verification claims in the PR body and commit message are, with one exception,
reproducible and accurate — including the exact test count. The defects are not
overstated verification; they are **two documented channels that do not work for a
reader today** (npm install, security reporting) and **one false factual claim**
(DeepWiki 404).

## Blocking

### B1. Quick Start advertises an npm package that does not exist — `README.md:53`, `README.zh-CN.md:45`

**[RAN]** `curl https://registry.npmjs.org/@vietairs/open-computer-use` → **404**.
`https://registry.npmjs.org/open-computer-use` → 200, `dist-tags.latest = 0.3.5`.

The README presents the install unconditionally:

```bash
npm i -g @vietairs/open-computer-use
```

with no "not yet published" caveat, followed immediately by "The npm package also
exposes `ocu` as the short CLI alias" — present tense, describing a package that
cannot be fetched.

Reader harm: from the moment this merges, every visitor to the fork's front page runs
a command that fails with `E404 Not Found`. Before this PR the same command was *wrong*
(it installed upstream 0.3.5) but *worked*. This PR converts a wrong-project install
into a broken install, and the README says nothing about it.

The PR body's Known Gap #1 frames `@vietairs` scope ownership as a **release-time**
risk ("`npm publish` fails with 403 at release time"). That framing under-states it:
the README is public the instant main merges, months before any publish. The gap is
disclosed to the *reviewer*, not to the *reader*.

Fix (docs-only, no scope decision needed): mark the install as pending until the first
publish, e.g. a `> [!NOTE]` above the block — "Not yet published to npm; build from
source with `swift build` / see Releases in the meantime" — in **both** READMEs, or
point Quick Start at the GitHub release asset which does exist (see B2 note).

### B2. SECURITY.md's primary reporting channel is disabled on this repo — `SECURITY.md:16`

**[RAN]** `gh api repos/vietairs/open-codex-computer-use/private-vulnerability-reporting`
→ `{"enabled": false}`.

`SECURITY.md:13-16` tells reporters to use
`https://github.com/vietairs/open-codex-computer-use/security/advisories/new`.
With private vulnerability reporting **off**, that page is not available to anyone
without write access — an external reporter gets a 404 after logging in.
(My unauthenticated `curl` returned 302 → `/login`, which is why a naive status check
looks green; the 200 in a `-L` check is the login page, not the form.)

The stated fallback, `SECURITY.md:18-19` — "reach the maintainer via their GitHub
profile [@vietairs]" — is not a channel either: GitHub has no direct messaging, and the
profile at github.com/vietairs publishes no contact address **[READ]**.

Reader harm: the PR's own stated problem is *"There was no working way to report a
vulnerability."* As merged, there still is not one. A researcher with a real finding
either gives up or files a **public issue** — the exact outcome `SECURITY.md:11`
forbids.

This is a one-click repo setting, not a code change: enable Settings → Security →
Private vulnerability reporting **before or with** the merge, and/or add a real contact
(an email you control) as the fallback. Until then the file promises a channel it does
not have.

- `docs/histories/2026-09/20260923-0024-fork-release-readiness.md:30-31` → "Removed the DeepWiki badge after confirming it 404s for the fork."

It does not 404. The *decision* is defensible — the fork's DeepWiki page is an empty

release badge return 200" — both **[RAN]** 200), which is what makes it costly: the
paragraph reads as uniformly status-code-verified, and one third of it is not.

Reader harm: a future maintainer re-evaluating the badge trusts the recorded status,
does not re-check, and inherits a wrong fact from the permanent history note. The
concrete correction: "removed because DeepWiki has not indexed the fork — the page
loads but is empty."

## Medium

### M1. Upstream routing points at a repo page, not a reporting channel — `SECURITY.md:33-38`

The direction itself is sound: inherited code paths genuinely belong upstream, and
saying "**also** consider" (rather than "instead") correctly avoids bouncing a reporter
away from a fork-specific bug. But the link is upstream's repo homepage, and
**[RAN]** `gh api repos/iFurySt/open-codex-computer-use/private-vulnerability-reporting`
→ `{"enabled": false}` — upstream has no private channel either.

Reader harm: a reporter told to "report to upstream" with only a repo link does the
obvious thing — opens a public issue on upstream. Say plainly that upstream has no
private advisory channel and that the reporter should contact the upstream maintainer
directly, or that this fork will relay the report.

### M2. First-person upstream prose under a fork note — `README.md:20`, `README.zh-CN.md:20`

`README.md:18-20` retains upstream's voice verbatim:

> "...so I decided to build an open-source version."
> "I started this repo with my [harness template](https://github.com/iFurySt/harness-template) ... I also wrote [a post](https://www.ifuryst.com/blog/2026/speedrunning-the-ai-era/) about the methodology behind it."

Eleven lines above, the new note (`README.md:9`) says the project is "maintained at
vietairs/open-codex-computer-use". Nothing between them re-attributes the "I".

Assessed fairly, this lands on the **acceptable** side rather than the misleading side,
for three verified reasons **[READ]**: the note at line 9 explicitly names
`iFurySt/open-codex-computer-use` as the source; the "I" sentence links to *iFurySt's*
harness-template and *ifuryst.com*'s blog inside the same sentence; and `plugin.json`
keeps Leo as author (confirmed in the diff — only `repository`/`homepage`/`websiteURL`/
`privacyPolicyURL`/`termsOfServiceURL` moved). A reader who reads both paragraphs can
tell who is speaking.

It is nonetheless ambiguous on a skim, and the cheap fix is one clause — "Upstream's
author writes:" before the paragraph, or "The prose below is upstream's." appended to
the fork note. Worth doing; not worth blocking.

**[RAN]** all three upstream attribution links resolve: harness-template 200,
ifuryst.com blog post 200, open-codex-browser-use 200.
