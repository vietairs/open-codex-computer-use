## BLOCKING

### B1-R2 — `supply-chain-security.yml` will fail on every PR and push **[RAN]**

`.github/workflows/supply-chain-security.yml:42` pins `go-version: "1.22.x"`.
`scripts/computer-use-cli/go.mod:3` declares `go 1.26.0`. With `GOTOOLCHAIN=auto`
(the runner default), the go command switches to the toolchain named by the go
directive — **exactly `go1.26.0`**, never a newer patch — before running anything
in that directory. govulncheck then scans a `go1.26.0` standard library.

Emulated the runner exactly (`GOTOOLCHAIN=go1.22.12+auto`, i.e. local Go 1.22
with auto switching) in `scripts/computer-use-cli`:

```
$ GOTOOLCHAIN=go1.22.12+auto go version
go version go1.26.0 darwin/arm64

$ GOTOOLCHAIN=go1.22.12+auto go run golang.org/x/vuln/cmd/govulncheck@v1.1.4 ./...
...
Vulnerability #17: GO-2026-4599
  Found in: crypto/x509@go1.26   Fixed in: crypto/x509@go1.26.1
Your code is affected by 17 vulnerabilities from the Go standard library.
exit status 3
rc=1
```

Under `set -euo pipefail` (line 65) a nonzero `go run` fails the step. **The
workflow is red today, on an unmodified checkout, for stdlib CVEs that have
nothing to do with the PR.**

Control: with the host toolchain `go1.27.1` (local ≥ required, so no switch
happens) the same command prints `No vulnerabilities found.` and exits 0.

Failure scenario: the first PR opened after this branch lands gets a red
required-looking check with 17 findings the author cannot fix, and the
predictable response is to delete the workflow.

Fix (one line): raise `go-version` to a value ≥ the go directive — e.g.
`go-version: "stable"` or `"1.26.x"`. Because the directive forces a *downgrade*
to 1.26.0 from 1.22, raising setup-go is the only lever that works; pinning
govulncheck differently does not help. Optionally add `toolchain go1.26.8` to
`scripts/computer-use-cli/go.mod` so the floor tracks patch releases.

Knock-on: the H2 pin rationale (workflow lines 59–62, commit `f43b936`) —
"v1.1.4 … matches the Go version this job installs" — is moot. The job never
runs govulncheck under Go 1.22 in the only module that gets scanned; the
toolchain is always ≥1.26 there. The pin itself is harmless (v1.1.4 builds and
runs fine under go1.26.0 and go1.27.1, both verified), but once `go-version` is
raised there is no reason not to move to v1.8.0.

## HIGH

### H1-R2 — the rescope still leaves two live pointers at upstream's npm package **[READ]**

1. `skills/open-computer-use/references/installation.md:40`
   ```sh
   npm update -g open-computer-use
   ```
   Unscoped. The install command two blocks above was rescoped to
   `@vietairs/open-computer-use`; the update command was not. A user who
   installs the fork and then asks the agent to update it gets upstream's
   package installed over it. This is the exact H1 defect, in the same file that
   was edited to fix H1.

2. `scripts/npm/build-packages.mjs:365` — generated launcher error text:
   ```
   Missing bundled native runtime for ${platformKey} at ${executablePath}.
   Reinstall with:
     npm install -g open-computer-use
   ```
   This string ships inside every published `@vietairs/*` tarball. On a
   platform-runtime miss, the fork's own binary instructs the user to install a
   different maintainer's package. Pre-existing (not introduced by the delta),
   but it is the same class and it is user-facing at runtime.

Everything else in `skills/` is clean: no `iFurySt` skill-source reference
survives (`npx skills add vietairs/…` in both places), and the caveat wording
matches both READMEs (`make app` / `scripts/build-open-computer-use-*.sh` —
verified all four exist: `Makefile:15` target `app`, three build scripts).

### M3-R2 — `validate-github-release-notes.mjs` was left behind by the L1 fix **[READ]**

`scripts/npm/build-packages.mjs:37-39` says its `resolveRepositoryURL()` *"mirrors
the resolveRepositoryURL() pattern in scripts/validate-github-release-notes.mjs"*.
They are now out of sync:

- `build-packages.mjs:52` → `/github\.com[:/](.+?)(?:\.git)?\/?$/` (fixed)
- `validate-github-release-notes.mjs:28` → `/github\.com[:/](.+?)(?:\.git)?$/` (old)

With an origin of `https://github.com/vietairs/open-codex-computer-use/`, the
validator resolves the slug to `vietairs/open-codex-computer-use/` and every
release-note URL check compares against a double-slashed URL. Two copies of one

`https://github.com/iFurySt/open-codex-computer-use` as the fallback. On a
checkout without an `origin` remote (a CI `actions/checkout` of a tag can
produce this in some configurations), the fork's release-note validation runs
against upstream's repo URL. `build-packages.mjs:41` has the same upstream
fallback, but there it is a deliberate, commented choice.
