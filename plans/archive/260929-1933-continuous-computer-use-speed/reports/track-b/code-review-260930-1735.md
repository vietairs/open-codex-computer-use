### Medium

**M1. The find_elements guidance for deep content tells the model to change something that has no effect on the walk.**
`ToolDefinitions.swift:165` ("for deep content in large trees, narrow by role plus label or use get_app_state") and
`skills/open-computer-use/SKILL.md:55-59` ("pass `role` plus `label` so the match is specific ... Do not raise `max_nodes`").
- Verified in `ElementSearchWalker.swift:168-198`: the node order and the budget do not depend on the query. `query.matches` only decides what counts as a hit. When a result says `truncated=true` with 0 hits, the budget ran out before the walk reached the target's depth. A more specific role and label reads the same first `max_nodes` nodes and finds the same nothing. Narrowing helps only in the other case: shallow matches fill `max_results` (`stoppedAtMaxResults`).
- Failure scenario: the model searches for a Mail message row with `role=AXRow, label="Invoice"`, gets `truncated=true` with 0 matches, follows the description and retries with `match: exact` or a longer label, and gets the same miss. That is a wasted round trip on each attempt. `max_nodes` is the one lever the tool has for this, and the SKILL text forbids it. For latency the ban makes sense: at about 3.7 ms per node, 10 000 nodes take about 37 s. But the text gives the wrong reason.
- Also, `get_app_state` truncates trees over 1200 nodes too (an accepted trade-off). It reaches deep content only because its walk is depth-first. The text does not say this.
- Fix: say it plainly. For example: "Searches breadth-first ...; truncated=true means the node budget ran out before deeper levels were read, and changing role or label will not reach them. Use get_app_state for deep content, or raise max_nodes (slow, about 4 ms per node)." Use the same reasoning in SKILL.md. If the ban on raising max_nodes is a deliberate product decision, keep it, but drop the "narrow by role plus label" advice for the truncated case.

**M2. `open_url` activates the handler app, which conflicts with outcome-lock decision 19.**
`ShortcutAndUrlLauncher.swift:145-148` passes a default `NSWorkspace.OpenConfiguration()`, and `activates` defaults to `true`. The handler (Chrome, Mail compose for `mailto:`) comes to the front and takes focus from the app the user is working in.
- Decision 19 (user, verbatim): "should not take the focus while i'm working on other tab or app", with "no activation, raise, or focus theft". Decision 20 says default-path activation elsewhere stops taking focus.
- The docs (`skills/.../references/scripting.md`) do not say that open_url brings the handler forward. The live check (live-measurement 2a) recorded only latency and isError, not a frontmost-app change.
- Failure scenario: the agent calls `open_url https://...` in the background while the user types in another app. Chrome comes to the front, and the user's next keystrokes go to Chrome.
- Fix: set `configuration.activates = false`, and add a unit seam or test that asserts the configuration. If activation is intended for open_url, record it as an explicit exception in outcome-lock and in scripting.md. This is a product decision, so it needs the user (see the unresolved questions).

### Low

**L1. The running-app list is frozen in the relay and in the plain stdio process.** `ScriptingDictionaryLookup.swift:569`.
- `get_scripting_dictionary` runs relay-locally. In relay mode, `MacOSAppAgentProxy.runProxy`, then `proxyMCP`, then `LocalChannelRouter.run` runs on the main thread, which is blocked in `readLine`. In the plain stdio direct mode (`OpenComputerUseMain.swift`, visual cursor off), the loop also runs on the main thread. Apple documents that `NSWorkspace.runningApplications`, and `NSRunningApplication` properties such as `isTerminated`, change only when the main run loop runs in a common mode. The MCPAppRuntime path runs the loop on a detached thread with a live main run loop, so it is fresh.
- The effect of d747be1's ranking: after the first lookup, an app launched later is not in the list, and a quit app is still `isTerminated == false`. The standard-directory and bundle-id fallbacks hide most cases. They do not cover apps outside `/Applications`, `/System/Applications` or `.../Utilities` looked up by name (for example `~/Applications`, or System Events started after the first call, the already-noted follow-up). A stale quit app only yields a static sdef read, so there is no security impact.
- This comes from documented API behavior. I did not observe it live: the sandbox blocks launching apps.
- Fix: in the relay, take a fresh snapshot per call, for example `RunLoop.main.run(mode: .default, before: .now)` before reading when on the main thread, or query LaunchServices directly. Alternatively, document that the name lookup reflects the apps running at the first call. Worth folding into the existing "System Events by name" follow-up.

**L2. The new tests pin less than their names say.**
- `ElementSearchTests.swift:794`, `testFindElementsDescriptionStatesBreadthFirstOrder`: its `contains("get_app_state")` assertion is vacuous. The description at 5d6fac8 already contained "(any get_app_state or action result)" (verified with `git show`). Only the "breadth-first" assertion pins anything. Suggest asserting the whole guidance sentence, or drop the second assertion.
- `ElementSearchTests.swift:489,511`, the `sameWindow(chosen, snapshotInitialWindow(...))` parity checks are tautological. `elementSearchWindowRoot` calls `SnapshotBuilder.initialWindow` itself, so they cannot fail independently. The explicit `CFEqual(..., usable/systemFocused)` assertions are the real pins, and they are adequate. No test puts a *different* app at the front with its own focused window, to prove that window is never chosen. Test 1 only covers "no focused app". The logic is shared with the snapshot, so the risk is low.
- `ScriptingDictionaryLookupTests.swift:506`, `bestRunningMatch`: no test pins the documented "enumeration order breaks ties". Every test has either one eligible candidate or candidates with different ranks. Changing `<` to `<=` at `:621` would pass the whole suite. Add two equal-rank `.app` candidates and assert that the first one wins.

**L3. The BFS queue grows past the budget.** `ElementSearchWalker.swift:193-198`.
- Children are enqueued for every node read, however little budget is left. With `maxNodes` up to 10 000 and wide AXChildren lists (web areas and groups are not row-capped), the queue can hold far more AXUIElement refs than will ever be read.
- DFS had the same property, and all refs are released on return, so this is minor. The real cost is the AXChildren IPC in `read`, not the enqueue.
- Optional: stop enqueuing once `queue.count - head >= query.maxNodes - nodesVisited`. Those nodes can never be read.

### Info

- I1. The doc comment at `ElementSearchAccessibilitySource.swift:138-140` claims the window is chosen "exactly as a snapshot chooses". It is not: the snapshot enables AXManualAccessibility and AXEnhancedUserInterface first (`AccessibilitySnapshot.swift:396`), and for Electron apps that can change whether a window exists at all. This is already recorded in impl-notes phase 05; only the comment overclaims.
- I2. The hits-only snapshot's `focusedElement` is app-level only (`ElementSearchAccessibilitySource.swift:168`). The snapshot uses the system-wide focus when the app is frontmost (`preferredFocusedElement`). This is pre-existing (fd4dc25, delta-reviewed) and noted here only because 9743c40 aligned the window choice but not the focus choice.
- I3. Light pass, no new defects: the router in relay, direct and MCPAppRuntime mode matches the old `server.run()` loop contract. Empty lines are skipped, one response per line, and forward errors propagate. MCPAppRuntime runs it on a detached thread, not the main thread. In `ConfinedChildProcessRunner`, every fd is closed on the error paths, and after `abandonDrain` the drain loop exits within one 50 ms poll, before the controller closes the read ends, so no fd-reuse race was found. `openWithCheckedHandler` bounds its wait by `openTimeoutSeconds`, and the completion handler is not delivered on main, so the relay cannot deadlock. A `run_script` blocks the single stdio loop for up to 60 s. The design accepts that serial behavior.
